# 🏠 Приёмка

MAX мини-приложение для приёмки работ в многоквартирном доме. Житель сообщает о проблеме, председатель назначает исполнителя, член совета проверяет результат по чек-листу, а акт подтверждают исполнитель и председатель.

## Задача и пользователи

Обращения, проверка результата и замечания часто живут в разных переписках и документах. «Приёмка» связывает их в одном воспроизводимом процессе с историей действий и документами. Роли дома: **RESIDENT** создаёт обращение; **CHAIRMAN** назначает исполнителя и проверяющего, завершает акт; **EXECUTOR** передаёт работу на проверку, устраняет замечания и первым подтверждает акт; **COUNCIL_MEMBER** проверяет и повторно проверяет работу. Системный администратор управляет доступом отдельно и не получает домовые workflow права автоматически.

## 🔄 Сценарий проверки

1. житель создаёт новое обращение в демо-доме → обращение появляется со статусом `NEW`
2. председатель назначает активного исполнителя → создаётся связанная Work, исполнитель видит задачу
3. исполнитель передаёт результат на проверку → появляется возможность назначить проверяющего
4. председатель назначает одного активного члена совета → backend создаёт snapshot чек-листа
5. проверяющий отвечает `PASS` или `FAIL` на каждый пункт и завершает проверку → каждый `FAIL` создаёт отдельный Issue
6. исполнитель отправляет устранение с комментарием и минимум одним фото → исходный проверяющий получает Reinspection
7. проверяющий отмечает `RESOLVED` или `NOT_RESOLVED` → при втором варианте Issue снова открыт; цикл продолжается до устранения всех замечаний
8. исполнитель подтверждает сформированный backend Acceptance Act, затем текущий председатель подтверждает его → Work и обращение становятся `ACCEPTED`

Для сценария без замечаний после ответов `PASS` на все пункты backend сразу формирует акт. Завершённые проверки и отправленные устранения неизменяемы. Подтверждение в приложении не является УКЭП.

## 🧩 Архитектура

| Часть | Назначение |
| --- | --- |
| `apps/web` | React, Vite и MaxUI, интерфейс внутри MAX |
| `apps/api` | Node.js 24, TypeScript, Fastify, Pino, Prisma; авторизация и переходы статусов |
| `packages/shared` | общие DTO и маршруты для frontend |
| MySQL 8.4 | дома, членства, работы, история, outbox и метаданные документов |
| Docker Compose | API и MySQL, отдельные volumes для media, PDF и логов |

MAX — реальная внешняя интеграция: мини-приложение передаёт raw `window.WebApp.initData`, API локально проверяет подпись и срок действия по `MAX_BOT_TOKEN`, а BotOutbox доставляет сообщения. Данные демо-дома и workflow в seed синтетические. Интеграции с ГИС ЖКХ в MVP нет; продукт её не имитирует. Для реального дома потребуются справочники дома, УК и исполнителей.

## 🚀 Локальный запуск

Нужны Docker и Docker Compose; для команд разработки — Node.js 24 и npm. Скопируйте `.env.example` в `.env`, задайте собственные `MAX_BOT_TOKEN`, `MAX_BOT_NAME`, `MAX_WEBHOOK_SECRET`, `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD`, `APP_PORT` и `PUBLIC_BASE_URL`. `.env` не попадает в Git. Пример переменных и defaults находится в [.env.example](.env.example).

```bash
docker compose up -d --build
```

API доступен на `http://127.0.0.1:${APP_PORT}/api/ready`; frontend обслуживается тем же приложением. `APP_PORT` задаёт свободный порт хоста, API внутри контейнера слушает `3000`. MySQL использует внутренний `3306` и не публикуется на хосте. Для MAX мини-приложения нужен внешний HTTPS reverse proxy к loopback API.

```bash
docker compose exec -T api npm run demo:seed  # синтетические данные, повторный запуск безопасен
docker compose stop                       # остановка без удаления volumes
docker compose up -d --build              # повторный запуск
```

Важные переменные: `COMPOSE_PROJECT_NAME` изолирует окружение и volumes; `MAX_INIT_DATA_MAX_AGE_SECONDS` задаёт срок подписи (обычно 3600 секунд); `MAX_OUTBOUND_ENABLED` по умолчанию `true`, а `false` выключает webhook setup и доставку BotOutbox; `ALLOW_SELF_ROLE_SWITCH` нужен только для отдельной демонстрации смены роли; `PREVIEW_ACCESS_REQUIRED` включает дополнительный gate; `BOT_TIME_ZONE`, `LOG_LEVEL`, `APP_LOG_DIR`, `LOG_RETENTION_DAYS` и `TRUSTED_PROXY_IP` настраивают время и логи. Пароли, токены и подписанные заголовки не храните в Git или review ZIP.

## 🧪 Тестовые данные и API

[docs/test-data.json](docs/test-data.json) содержит демо-дом «Демо: ул. Примерная, д. 12», компанию «Демо УК» и синтетические MAX ID: житель `7000000000000000101`, член совета `7000000000000000102`, председатель `7000000000000000103`, исполнитель `7000000000000000104`, администратор `7000000000000000105`. Это идентификаторы, не credentials. Внутренние `houseId`, `userId`, `observationId` и `workId` извлекайте из API при каждом прогоне.

Проверка API: [DATA-API.yaml](docs/DATA-API.yaml) задаёт основные воспроизводимые шаги; [OpenAPI](docs/openapi.json) описывает полный контракт; [API-FRONTEND.md](docs/API-FRONTEND.md) содержит примеры и правила frontend. Подписанные `X-Max-Init-Data` для EVAL передаются отдельно в технических материалах сдачи. `POST /api/media` принимает JPEG/PNG/WebP до 10 MiB; фото привязываются к обращениям и замечаниям по `mediaId`. Отчёты проверок, мотивированный отказ и акт формируются сервером как PDF со snapshot и SHA-256; приватные ссылки на media и документы требуют доступа.

Для локальной проверки используйте [Postman collection](docs/postman/Priemka.postman_collection.json) и `npm run postman:signer -w @priemka/api`. Signer использует локальный токен и не создаёт обход авторизации.

## 🌐 Окружения и ограничения

Push в `backend` автоматически проверяет и развёртывает DEV, push в `main` — PROD. EVAL развёртывается только ручным **Deploy EVAL** по конкретному commit SHA. Публичный API проверки: [eval-priemka.ithube.ru](https://eval-priemka.ithube.ru). EVAL имеет отдельную БД и volumes, синтетических пользователей и 50-дневные initData; outbound MAX на нём отключён. Подробности без серверных секретов — в [docs/DEPLOY.md](docs/DEPLOY.md).

Ограничения MVP: данные seed не представляют реальные дома; ГИС ЖКХ не подключена; подтверждение акта не является квалифицированной электронной подписью. Для локального запуска нужен действительный MAX bot token, если проверяется авторизованный сценарий.
