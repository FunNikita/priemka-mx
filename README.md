# Приёмка — MAX мини-приложение

Монорепозиторий хакатонного MVP: Fastify API, Prisma/MySQL, frontend и общие TypeScript DTO. Актуальные маршруты и примеры для frontend описаны в [docs/API-FRONTEND.md](docs/API-FRONTEND.md). Runtime-источник контракта — схемы Fastify; [OpenAPI](docs/openapi.json) экспортируется из них.

## Локальный запуск

Скопируйте `.env.example` в `.env`, задайте собственные значения секретов, `MAX_BOT_NAME` и `APP_PORT`. `.env` не добавляйте в Git. Запустите `docker compose up -d --build`. Доступность API: `http://127.0.0.1:${APP_PORT}/api/ready`. MySQL не публикуется на порт хоста.

Для тестовых данных на свежей БД выполните `docker compose exec api npm run demo:seed`. Seed повторяемый и добавляет демо-дом, роли, шаблоны, работы на разных этапах, замечания и документы без сброса БД. Синтетические MAX ID: `7000000000000000101` (житель), `7000000000000000102` (член совета), `7000000000000000103` (председатель), `7000000000000000104` (исполнитель), `7000000000000000105` (системный администратор).

## Сценарий MVP

1. Пользователь входит через MAX и вступает в дом. При `ALLOW_SELF_ROLE_SWITCH=true` активный участник меняет свою домовую роль через `PATCH /api/me/houses/:houseId/membership`. Для исполнителя нужна компания. В доме одновременно максимум один активный председатель.
2. Житель или председатель создаёт обращение через `POST /api/houses/:houseId/observations`. Председатель назначает исполнителя через `PUT /api/observations/:observationId/executor`; backend создаёт внутреннюю Work. Исполнитель вызывает `POST /api/works/:workId/submit-for-inspection` после выполнения.
3. Председатель назначает одного проверяющего. Backend проверяет категорию чек-листа и копирует его в snapshot; пункт получает `PASS` или `FAIL`. Для `FAIL` нужен комментарий до 512 символов или до пяти фотографий. Каждый `FAIL` создаёт отдельное замечание.
4. Исполнитель устраняет все замечания. Каждая отправка — отдельная `Remediation`; исходный проверяющий завершает `Reinspection`.
5. Backend формирует акт после проверки без замечаний или устранения всех замечаний. Исполнитель подтверждает его первым, текущий активный председатель — вторым. Один пользователь может выполнить обе стороны после смены роли. Обращение и внутренняя Work становятся `ACCEPTED`.

Системный администратор имеет отдельный API пользователей и членств, но сам по себе не действует за председателя, исполнителя или проверяющего. Старые поля полномочий в БД не участвуют в новом workflow.

## Проверки и инструменты

```bash
npm run lint
npm run typecheck
npm test
npm run build
npm run openapi:export
```

[Postman collection](docs/postman/Priemka.postman_collection.json) поддерживает локальную проверку с синтетической MAX подписью. Для неё запустите `npm run postman:signer -w @priemka/api`; signer использует только локальный `.env`. Не сохраняйте реальные `initData` и токены в коллекцию или Git.

Подготовка будущего DEV/PROD развёртывания описана в [docs/DEPLOY.md](docs/DEPLOY.md). GitHub Actions и серверная настройка выполняются отдельной задачей.
