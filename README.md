# 🏠 Приёмка

MAX мини-приложение для приёмки работ в многоквартирном доме. Житель сообщает о проблеме, председатель назначает исполнителя, член совета проверяет результат по чек-листу, а акт подтверждают исполнитель и председатель.

## 💡 Что решает «Приёмка»

- **Проблема:** обращения, результаты работ и замечания часто остаются в разных переписках и документах.
- **Приоритетный сегмент:** житель многоквартирного дома, который сообщает о проблеме общего имущества, и совет дома, который контролирует результат выполненных работ.
- **Результат:** прозрачный путь от обращения жителя до проверенной и принятой работы с замечаниями, чек-листами и документами в одном месте.

## 👥 Роли

| Роль | Код | Что делает |
| --- | --- | --- |
| Житель | `RESIDENT` | Создаёт обращение и следит за его статусом. |
| Председатель | `CHAIRMAN` | Назначает исполнителя и проверяющего, затем подтверждает акт приёмки. |
| Исполнитель | `EXECUTOR` | Передаёт работу на проверку, устраняет замечания и первым подтверждает акт. |
| Член совета | `COUNCIL_MEMBER` | Проверяет работу по чек-листу и проводит повторную проверку. |

Системный администратор (`User.isAdmin=true`) не является домовой ролью и сам по себе не получает права на действия в процессе приёмки.

## 🔄 Основной сценарий

1. **Житель** создаёт обращение в демо-доме. Обращение получает статус `NEW`.
2. **Председатель** назначает активного исполнителя. Создаётся связанная работа (Work), которую видит исполнитель.
3. **Исполнитель** передаёт работу на проверку.
4. **Председатель** назначает одного активного члена совета. Сервер сохраняет снимок чек-листа (snapshot).
5. **Проверяющий** отвечает `PASS` или `FAIL` на каждый пункт и завершает проверку. Каждый `FAIL` создаёт отдельное замечание (Issue).
6. **Исполнитель** отправляет устранение (Remediation) с комментарием и минимум одним фото. Исходный проверяющий получает повторную проверку (Reinspection).
7. **Проверяющий** отмечает `RESOLVED` или `NOT_RESOLVED`. Во втором случае замечание снова открывается; цикл продолжается до устранения всех замечаний.
8. **Исполнитель** первым подтверждает акт приёмки (Acceptance Act), затем его подтверждает текущий председатель. Работа и обращение становятся `ACCEPTED`.

При ответах `PASS` на все пункты сервер сразу формирует акт приёмки. Завершённые проверки и отправленные устранения неизменяемы. Подтверждение акта в приложении не является УКЭП.

Основной сценарий выполняется внутри MAX. Мини-приложение предназначено для мобильной и веб-версий MAX. В него входят реальные MAX-аккаунты с активными ролями дома. Синтетические MAX ID используются только для проверки API в EVAL.

## 🧩 Архитектура

| Компонент | Технологии | Ответственность |
| --- | --- | --- |
| Мини-приложение (`apps/web`) | MAX, React, Vite, MaxUI | Интерфейс ролей, формы, чек-листы и обращения к API. |
| Серверная часть (`apps/api`) | Node.js 24, TypeScript, Fastify, Pino, Prisma | Проверка MAX-авторизации, переходы статусов, документы, медиафайлы и очередь уведомлений BotOutbox. |
| Общий контракт (`packages/shared`) | TypeScript | Маршруты API и общие типы данных (DTO) для интерфейса и сервера. |
| База данных | MySQL 8.4 | Пользователи, дома, членства, работы, проверки, замечания, история и метаданные документов. |
| Хранилище файлов | Тома Docker (volumes) | Фото, PDF и журналы сервера. |
| MAX Bot API | Внешняя интеграция | Уведомления, ссылки в MAX и выдача документов через бота. |
| Запуск | Docker Compose | Воспроизводимый запуск API и MySQL. |

Мини-приложение передаёт исходное `window.WebApp.initData` серверу, который локально проверяет подпись и срок действия с помощью `MAX_BOT_TOKEN`. Очередь BotOutbox доставляет сообщения через MAX Bot API. Демо-дом и данные процесса синтетические. Интеграции с ГИС ЖКХ в MVP нет; для реального дома потребуются справочники дома, управляющей организации и исполнителей.

## 🚀 Локальный запуск

Для запуска необходимы Docker и Docker Compose; для команд разработки — Node.js 24 и npm. Версии npm-зависимостей зафиксированы в `package-lock.json`. Перед запуском необходимо создать `.env` на основе [.env.example](.env.example) и указать собственные значения секретов, порта и публичного адреса. `.env` не входит в Git.

```bash
docker compose up -d --build
```

После запуска API доступен на `http://127.0.0.1:${APP_PORT}/api/ready`; интерфейс обслуживается тем же приложением. `APP_PORT` — свободный порт хоста, внутри контейнера API слушает `3000`. MySQL использует внутренний `3306` без публикации на хосте. Для мини-приложения MAX необходим внешний HTTPS reverse proxy к API на loopback.

Синтетические данные, остановка без удаления томов Docker и повторный запуск:

```bash
docker compose exec -T api npm run demo:seed
docker compose stop
docker compose up -d --build
```

Повторный запуск `demo:seed` безопасен.

## 🧪 Тестовые данные

[docs/test-data.json](docs/test-data.json) содержит синтетический набор для EVAL:

- дом: «Демо: ул. Примерная, д. 12»
- организация-исполнитель: «Демо УК»
- Житель (`RESIDENT`): `7000000000000000101`
- Член совета (`COUNCIL_MEMBER`): `7000000000000000102`
- Председатель (`CHAIRMAN`): `7000000000000000103`
- Исполнитель (`EXECUTOR`): `7000000000000000104`
- Администратор: `7000000000000000105`

Это синтетические MAX ID, а не учётные данные для входа. Внутренние `houseId`, `userId`, `observationId`, `workId` и другие ID извлекаются из ответов API при каждом прогоне.

### Проверка API

- [DATA-API.yaml](docs/DATA-API.yaml) — воспроизводимый сценарий автоматической проверки по схеме DATA-API 1.0.
- [OpenAPI](docs/openapi.json) — полный контракт API.
- [API-FRONTEND.md](docs/API-FRONTEND.md) — правила интеграции интерфейса с API.
- [test-data.json](docs/test-data.json) — синтетические данные EVAL.
- [Коллекция Postman](docs/postman/Priemka.postman_collection.json) — локальная ручная проверка.

Публичный API для технической проверки доступен по адресу `https://eval-priemka.ithube.ru`. Защищённые запросы используют подписанные данные MAX в заголовке `X-Max-Init-Data`.

Каждый прогон DATA-API создаёт новые тестовые обращения и получает связанные ID из предыдущих ответов API. EVAL использует отдельную синтетическую базу данных.

DATA-API автоматически проверяет путь без замечаний до `ACCEPTED` и отдельную ветку до создания замечания после `FAIL`. Полный цикл устранения с фотографией, повторной проверкой, `RESOLVED` и актом проверяется в MAX: схема DATA-API 1.0 не определяет стандартный способ передать файл в multipart-запросе. `POST /api/media` принимает JPEG, PNG и WebP до 10 MiB; фото привязываются по `mediaId`.

Отчёты проверок, мотивированный отказ и акт формируются сервером как PDF со снимком данных и SHA-256. Фото и PDF выдаются по непредсказуемым ссылкам доступа (capability URL) `/photo/:key` и `/doc/:key.pdf`. Наличие ссылки даёт доступ к соответствующему файлу без `X-Max-Init-Data`:

- ответы исключаются из индексации через `X-Robots-Tag: noindex`
- фото дополнительно выдаются с `Cache-Control: private, no-store`
- перед выдачей PDF сервер проверяет целостность файла

Для локальной ручной проверки можно использовать [коллекцию Postman](docs/postman/Priemka.postman_collection.json) и команду `npm run postman:signer -w @priemka/api`. Скрипт подписи использует локальный токен.

## ⚠️ Ограничения MVP

- Демонстрационный набор содержит только синтетические данные и не представляет реальные дома.
- Интеграция с ГИС ЖКХ отсутствует и не имитируется.
- Подтверждение акта не является квалифицированной электронной подписью.
- Для авторизованного локального сценария требуется действительный токен MAX.
- Ссылка доступа к фото или PDF открывает файл любому, у кого она есть.
