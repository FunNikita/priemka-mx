# Правила frontend-разработки

## Git

- Работать только в ветке `frontend`, если Арина прямо не попросила иначе. Не коммитить напрямую в `main`.
- Не выполнять `git commit` без явного разрешения Арины. Можно предложить момент и текст коммита, затем дождаться разрешения.
- Не выполнять `git push` и не создавать Pull Request без прямой команды Арины. Никогда не выполнять force push и не merge'ить PR самостоятельно.
- Не делать rebase и не переписывать историю Git без прямого разрешения.
- Перед pull, merge или rebase проверять `git status` и беречь незакоммиченные изменения.
- Использовать только уже настроенную Git identity Арины. Не менять global git config. Если identity отсутствует, сообщить об этом.
- Не добавлять в коммиты, PR, код или metadata упоминания агента, включая `Co-authored-by`, `Codex`, `OpenAI`, `Generated-by` и `AI`.
- Сообщения коммитов писать только по-русски, кратким описанием результата: «Добавлен интерфейс страницы работ», «Перенесены компоненты главной страницы», «Исправлено отображение нижней навигации», «Обновлены зависимости frontend».

## Pull Request

- Будущий PR направлять из `frontend` в `main` только по прямой команде Арины.
- Перед предложением PR показать краткий diff/stat.
- Не merge'ить PR самостоятельно и не менять backend в PR без необходимости.

## Область работы

- Основная зона работы — `apps/web`. Не менять `apps/api` без отдельной задачи.
- Менять `packages/shared` только если frontend действительно нужен общий контракт.
- Менять корневые конфиги только при необходимости для frontend и объяснять причину.
- Не ломать Docker, API и MAX-инфраструктуру ради frontend.

## Экономия времени и токенов

- Сначала читать только нужные файлы. Не читать целиком `package-lock.json` без необходимости и не выводить огромные логи.
- Использовать `git status --short` и `git diff --stat` перед большим diff. Не повторять команды, результат которых уже известен.
- Сначала проверять `apps/web`. Не запускать полный backend test-suite после изменений CSS или React-компонентов.
- Полные lint, typecheck и build запускать перед предлагаемым коммитом или после значительных изменений.
- Не устанавливать зависимости на всякий случай; сначала искать решение существующими средствами.

## Безопасность

- Не помещать секреты во frontend. Значения `VITE_*` считать публичными. `MAX_BOT_TOKEN` никогда не должен попадать во frontend.
- Не логировать `X-Max-Init-Data`. Не коммитить `.env`.
- Перед разрушительными Git-командами или командами файловой системы остановиться и запросить разрешение.

## Backend API и контракт frontend

Актуальный backend-контракт брать из `origin/main`.

Основные локальные файлы frontend-контракта:

- `packages/shared/src/api.ts` — главный TypeScript-контракт: DTO, статусы, query/body/response и `apiRoutes`;
- `packages/shared/src/index.ts` — публичные exports `@priemka/shared`;
- `docs/API-FRONTEND.md` — русское описание использования backend API;
- `docs/openapi.json` — полный опубликованный HTTP-контракт;
- `docs/postman/Priemka.postman_collection.json` — запросы для ручной проверки API;
- `apps/web/src/api.ts` — общий helper `apiFetch`, который добавляет `X-Max-Init-Data`.

Если локальные backend-файлы ветки `frontend` отстают от `main`, фактическое поведение проверять по актуальному `origin/main`:

`git show origin/main:apps/api/src/houses.ts`
`git show origin/main:apps/api/src/business.ts`
`git show origin/main:apps/api/src/workflow.ts`
`git show origin/main:apps/api/prisma/schema.prisma`

Приоритет источников:

1. Фактические Fastify schemas и backend в `origin/main`.
2. `docs/openapi.json`.
3. `packages/shared/src/api.ts`.
4. `docs/API-FRONTEND.md`.

Frontend не должен придумывать отсутствующие API. Не менять `apps/api` без отдельной задачи.

### Правила интеграции API

- Использовать относительные `/api/*`.
- Запросы выполнять через существующий `apiFetch`.
- Не писать отдельную login-систему.
- Передавать исходный `window.WebApp.initData` только через `X-Max-Init-Data`.
- Не использовать `initDataUnsafe` как доверенный источник прав.
- Не передавать от frontend доверенные `userId`, `role`, `status`, `isAdmin`.
- MAX user/chat ID не преобразовывать в JavaScript `Number`.
- Использовать DTO и `apiRoutes` из `@priemka/shared`.
- Для доступности действий использовать `actions`, возвращаемые backend, вместо дублирования матрицы `role + status` во frontend.
- Backend является владельцем переходов статусов.
- После mutation обновлять данные с backend, а не менять бизнес-статус только локально.
- Для HTTP `204` не вызывать `response.json()`.
- Для HTTP `409` перечитать актуальную сущность.
- Фото сначала загружать через `POST /api/media`, затем использовать полученный `mediaId` в `mediaIds`.
- `URL.createObjectURL()` использовать только для локального preview.
- Не хранить во frontend `MAX_BOT_TOKEN`, `DATABASE_URL`, пароли или другие backend secrets.
- Значения `VITE_*` считать публичными.

### Пользовательские роли

Домовые роли:

- житель (`RESIDENT`);
- член совета (`COUNCIL_MEMBER`);
- председатель (`CHAIRMAN`);
- исполнитель (`EXECUTOR`).

`User.isAdmin=true` — системный администратор, а не роль дома.

Рабочие права обычного участника действуют только при активном членстве (`ACTIVE`).

Председатель рассматривает заявки обычных жителей, но не выдаёт повышенные роли.

Исполнитель видит только свои работы, не общий поток наблюдений жителей и не домовой чат.

### Главный workflow

Исполнитель передаёт выполненную работу
→ председатель назначает ровно одного активного члена совета
→ проверяющий проходит snapshot чек-листа
→ каждый `FAIL` создаёт отдельное замечание
→ исполнитель отправляет новую попытку устранения с комментарием и фото
→ тот же проверяющий выполняет повторную проверку
→ цикл повторяется до устранения
→ исполнитель создаёт и первым подтверждает акт
→ уполномоченный представитель дома подтверждает вторым
→ работа становится принятой (`ACCEPTED`).

`UNABLE_TO_CHECK` требует комментарий и блокирует завершение проверки.

Завершённые Inspection/Reinspection и отправленные Remediation не редактируются задним числом.

### Важные текущие ограничения API

На текущем backend пока нет публичного API:

- создания/передачи новой Work исполнителем на приёмку;
- CRUD повышенных ролей для frontend;
- списка `HouseObject`;
- редактирования/удаления комментариев;
- отдельного изменения статуса Observation;
- полного workflow MAX-уведомлений.

Не имитировать эти операции только локальным состоянием UI.

Для полного описания методов и текущих ограничений сначала читать `docs/API-FRONTEND.md`.
